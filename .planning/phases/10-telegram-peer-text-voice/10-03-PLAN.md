# Plan 10-03 — Chat output pipeline: fence-aware 4096 chunking, MarkdownV2 escaping, throttled edit-and-spill streaming (D-03)

## Phase Goal

**As a** developer away from my IDE, **I want to** drive ass-guard from a Telegram chat — full SDD scenarios over text and voice, on the same engine ACP uses — **so that** the agent keeps working wherever I am as a peer surface, not a stripped-down remote.

**This plan's slice:** the output half of D-03 (live throttled streaming), built as pure offline-testable logic. Assistant transcripts vastly exceed Telegram's 4096-after-entities cap, MarkdownV2 400s on the first unescaped reserved char, and `sendMessage`/`editMessageText` are both rate-limited with `retry_after` on 429 — Pitfall 12's minefield. This plan resolves it once, in one package, behind a Sender seam the bot loop (10-04) plugs go-telegram/bot into. The user-visible contract: multi-minute turns feel alive (throttled edits), long transcripts arrive as readable chunks, code blocks never break mid-fence.

## Truths

- Carries D-03 (locked: live throttled streaming, rate-limit-aware in-place edits with retry_after, spilling at the 4096 fence-aware boundary) and the TG-03 output clause; CONTEXT Discretion explicitly delegates "throttle interval/strategy details, edit-coalescing heuristics, MarkdownV2 escaping edge cases" — the concrete choices below are the documented discretion decisions.
- Research ground truth: PITFALLS Pitfall 12 (4096 UTF-8 chars AFTER entity parsing; no mid-entity/mid-fence splits; the MarkdownV2 escape set `_*[]()~>#+\-=|{}.!`; ~1 msg/s per chat, ~30/s global, both verbs rate-limited, 429 carries retry_after; "v1 output policy: throttled progress edits, a fence-aware splitter, a token-bucket limiter (1/s per chat) with retry_after-aware backoff"); FEATURES Area 4 ("Map ACP session/update stream → message edits; edit-rate throttle per Telegram limits"; comparables' pattern: throttled edits + persistent working indicator).
- Discretion decisions: (1) throttle interval default **1500ms** between edits per chat (under the ~1/s sustained class, tunable const); (2) coalescing = flush-at-interval of the accumulated buffer (chunk stream appends to a buffer; the flush sends the whole buffer so far as one edit — an edit is idempotent over the growing text); (3) spill decision at flush time: if escaped-buffer length would exceed 4096, finalize current message and open a new one (never edit-truncate); (4) escaping strategy = escape everything reserved OUTSIDE code spans/fences, pass code verbatim (model output is markdown-first; fences are where correctness matters most); (5) plain-text fallback helper for the rare API 400 — send the failing chunk without parse_mode (bounded recovery, one retry, then drop with stderr note).
- Deferred (CONTEXT "Deferred Ideas" + research): Telegraph-article escape hatch — documented future option, NOT built here; TTS/buttons — never.
- The escaper and splitter are also used by the voice-transcript echo and error messages in later plans — they are the ONE output policy (no per-callsite formatting).

<objective>
Build `internal/telegram`'s output pipeline as three pure, table-tested components: `SplitFenceAware` (rune-safe, fence-and-entity-aware ≤limit chunker that reopens long fences), `EscapeMarkdownV2` (reserved-char escaper with code passthrough), and `MessageSink` (coalescing throttled editor over a `Sender` seam: interval flushes, 429 retry_after backoff, 4096-after-escaping spill to a new message, Finalize on turn end). No network, no go-telegram dependency — the seam is the contract plan 10-04 implements.
</objective>
