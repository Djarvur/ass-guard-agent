# Plan 10-04 — Telegram bot loop: chat↔session binding, allowlist, text turns on the shared engine, `/stop`+`/new`, long-poll lifecycle

## Phase Goal

**As a** developer away from my IDE, **I want to** drive ass-guard from a Telegram chat — full SDD scenarios over text and voice, on the same engine ACP uses — **so that** the agent keeps working wherever I am as a peer surface, not a stripped-down remote.

**This plan's slice:** the frontend itself. Add `go-telegram/bot` v1.23.0 (the milestone's pinned dep), run the long-poll loop with the Phase-0 verified hygiene, bind each chat to a stable `tg-<chatID>` session on the shared `runtime.Runner`, gate access with an allowlist, stream turn output through the 10-03 sink, wire `/stop` and `/new`, and surface engine-ask as a chat message. After this plan a user can run a full text SDD scenario from a chat (given a launch mode, wired in 10-07) — `/opsx:*` arrives free because expansion lives in the session layer the Runner already is.

## Truths

- Carries TG-02 (long-poll, deleteWebhook, stable IDs + resume, drain) and the text legs of TG-03 (allowlist, `/stop`, `/opsx:*` from chat, engine-ask as message); D-02's mechanics (Discretion on parsing details — resolved below).
- Research ground truth: STACK Feature 4 (the exact shape: `bot.New` + handler registration + `Start(ctx)` in a goroutine; voice flow API names; no webhook, ever); VERIFIED-FACTS #5 (v1.23.0 stdout-silence verified by source inspection — zero `os.Stdout` in the library; `WithErrorsHandler` routes errors to `log.Printf`→stderr; NO `WithDebug` keeps the debug path silent; `WithSkipGetMe` keeps `New()` offline for tests; context cancel drains in < 2s in the spike); PITFALLS 11 (chat-scoped IDs never merged with ACP IDs; Session.Prompt not concurrent-safe → one turn per chat) and 12 (deleteWebhook before first poll; long-poll ctx from the server-lifecycle ctx; shutdown drain < 5s).
- Hard ordering: depends_on 10-01 (the Runner being consumed), 10-02 (redactor before the FIRST Telegram HTTP call — this plan makes them), 10-03 (the sink being streamed into).
- D-02 discretion resolutions (documented): (1) `/new` rebinds the chat to `tg-<chatID>-<n+1>` where n = the lexically greatest existing suffix (transcript filenames under `.ass-guard/transcript_tg-<chatID>*`), closing the old session first; on startup the chat resumes the LATEST transcript in that family — so `/new` is real (fresh session, fresh transcript) AND restart-resume is real (you come back to your newest conversation). (2) `/stop` = cancel the per-chat turn ctx (the exact mechanism ACP's session/cancel rides — D-16 semantics, transcript records cancellation). (3) An unknown chat gets silence + a stderr line (no capability leak to strangers); empty allowlist = deny all + one loud startup warning (secure default). (4) A second message while a turn runs is rejected with a one-line chat reply naming `/stop` (Session.Prompt is not concurrent-safe — Pitfall 11; the queueing alternative is deliberately NOT built: cancellation-first matches the safety model).
- Engine-ask: today the engine emits an `EngineDecision` (action=ask) on the bus and the ACP adapter surfaces it as a session/update; the Telegram frontend subscribes `EngineDecision` during the turn and renders `action=ask` decisions via `SendMessageDirect` (Discretion: format = `engine asks: <reason>` + the situation line — plain text, never buttons; the no-confirmation-tier rule is surface-independent).
- The frontend is constructed by CALLERS (10-07's two launch modes); this plan exports the constructor and proves everything against a fake Bot API server (httptest) — the same live-shape, offline-cost pattern the scheduler factory tests use.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram cloud → long-poll updates → handlers → Runner | Fully untrusted remote input (any Telegram user can message a bot) reaches the engine turn path. |
| Runner/model output → sink → Telegram API | Model-authored text becomes outbound messages (formatting-spoofing surface closed by 10-03). |
| bot token (config/env) → library → HTTP | The credential in transit; any echo is a leak (10-02 is the net; this plan adds the no-proactive-logging rule). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-13 | Elevation/abuse | unauthorized chats driving the agent | mitigate | allowlist gate BEFORE any Runner.Run or reply (Test 12); empty allowlist = deny-all + loud warning (secure default); strangers get silence (no capability oracle). |
| T-10-14 | Information disclosure | bot token via library errors/URLs | mitigate | WithErrorsHandler → slog → stderr ONLY (Test 5/6); never log request URLs; 10-02's redactor catches residual shapes (defense in depth); token never crosses into Runner/prompt text. |
| T-10-15 | Tampering | concurrent Prompt interleaving corrupting a session (Pitfall 11) | mitigate | one-turn-per-chat busy guard (Test 11); tg- namespace can never collide with ACP session ids (Test 10). |
| T-10-16 | DoS | message flood from an allowlisted chat | accept | one-turn-at-a-time + turn guard reply bounds concurrent work; allowlist is operator-curated (small set); no rate limiter on INBOUND messages in v1 (documented acceptance — the allowlist is the trust boundary). |
| T-10-17 | DoS | shutdown hang on a stuck long-poll (wrong ctx parent) | mitigate | poll ctx derived from the lifecycle ctx (Test 4); drain asserted < 5s. |
</threat_model>
