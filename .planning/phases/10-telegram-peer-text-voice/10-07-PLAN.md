# Plan 10-07 — Launch modes (`ass-guard telegram` + `acp serve --telegram`), the one drain path, and the LIVE phase gate

## Phase Goal

**As a** developer away from my IDE, **I want to** drive ass-guard from a Telegram chat — full SDD scenarios over text and voice, on the same engine ACP uses — **so that** the agent keeps working wherever I am as a peer surface, not a stripped-down remote.

**This plan's slice:** D-01's both-modes decision made real, TG-06, the drain unification of TG-02, and the phase's live gate. The `telegram` subcommand is a launch MODE for the Telegram interface (PROJECT.md's amended Out-of-Scope line already says exactly this — no doc change needed); `acp serve --telegram` runs the frontend as a sidecar beside the editor. Both call the same `runtime.New` + `NewFrontend`; shutdown is one function both modes funnel through; and the phase closes only on live evidence — a real chat driving a full text SDD scenario plus a transcribed voice turn, with the token canary grepped clean.

## Truths

- Carries D-01 (both modes, shared core builder, never a copied runACPServe), TG-06, TG-02's shutdown/stdout clauses, and the live legs of TG-03/TG-04 (the gate requires real-chat evidence).
- Research ground truth: PITFALLS Pitfall 11 (traps 1-2: editor kills Telegram = DEFINED clean-cancel behavior in combined mode, documented; telegram-only must REUSE the shared builder, not copy `runACPServe`; drain order "stop accepting prompts → grace for in-flight turns → stop the poll loop → close sessions; SIGTERM and stdin-EOF take the SAME path (turn EOF into ctx cancel)") and Pitfall 12 (long-poll ctx from the server-lifecycle ctx; drain < 5s test); SUMMARY Phase-3 deliverable ("telegram cobra subcommand + acp serve --telegram sidecar; one-drain-path shutdown; stdout byte-clean in both modes"); VERIFIED-FACTS #5 (the stdout-collision test generalized: both frontends in one process, zero non-ACP bytes).
- PROJECT.md line 76 is ALREADY amended ("`acp serve` and `telegram` are launch modes for those two interfaces, not CLI surfaces (amended at Phase-10 discussion 2026-08-14)") — this plan implements what the amendment describes; no PROJECT.md edit task.
- Discretion decisions: (1) the shutdown helper lives in `cmd/ass-guard` as a small function both entrypoints call (cancel ctx → wait for Frontend.Run to return with a bounded 5s timeout → CloseAllSessions) — ONE definition, referenced twice; (2) `--telegram` is OFF by default (opt-in sidecar; existing editor behavior untouched); (3) in combined mode, an unserviceable Telegram config (no token) with `--telegram` set degrades loudly to stderr and the ACP side continues (the engine serves the editor first — loud-but-never-fatal); telegram-only with no token is a hard startup error (nothing else to serve).
- The live gate mirrors the Phase-8 08-06 / Phase-9 09-04 pattern: automate everything automatable first (both modes' lifecycle tests run offline against the fake Bot API), then ONE operator checkpoint with a written script and evidence capture. The evidence artifacts are the `tg-` transcripts + canary greps + the operator's confirmation.
- Hard deps: all prior plans (the Runner, the frontend+voice, the STT seam, the redactor net).
