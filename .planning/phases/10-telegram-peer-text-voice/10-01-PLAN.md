# Plan 10-01 — `internal/runtime` extraction: the turn core becomes the shared engine home (THE structural refactor)

## Phase Goal

**As a** developer away from my IDE, **I want to** drive ass-guard from a Telegram chat — full SDD scenarios over text and voice, on the same engine ACP uses — **so that** the agent keeps working wherever I am as a peer surface, not a stripped-down remote.

**This plan's slice:** the prerequisite refactor, sequenced FIRST by ROADMAP/CONTEXT decision. Everything that makes a turn a turn — `sessionTurnRunner` and its engine/hook-DAG/MCP/expansion/skills/capturer wiring, constructed by `runACPServe` in `cmd/ass-guard/acp_serve.go` — moves into a new `internal/runtime` package with ONE exported builder (`runtime.New`). After this plan there are two consumers of one core (ACP today, Telegram next plan-set) and no copied construction path anywhere (TG-01; Pitfall 11's "extract core construction into a shared builder" mitigation, executed literally).

## Truths

- Carries TG-01 and the CONTEXT Discretion item "internal/runtime extraction mechanics (mechanical move — planner sequences it as the phase's first work)".
- **Hard dependency on Phases 8+9 having executed** (ROADMAP "Depends on"): the code being moved includes 08-04's expansion wiring + 08-05's skills wiring in `sessionFor` + 08-06's chaining plumbing, and 09-01's `makeProvider(capturer)` → `BuildWithCapturer` + per-session `TranscriptWriter` + `serveCtx` wiring + 09-05's `BodyStore` wiring + 09-06's audit `Mirror` default-on wiring — all of which land in `cmd/ass-guard/acp_serve.go` in those phases. This plan moves WHATEVER is on disk at execution time; the interfaces block below describes the expected post-Phase-9 shape from the committed plan files (09-01-PLAN.md above all). If Phase 9's landed code differs in detail from the plan files, the move mechanics are unchanged — move what exists, verify behavior via the existing tests.
- Research ground truth: ARCHITECTURE.md "nothing rewrites a v1.0 component; every feature is a new leaf package" — `internal/runtime` is exactly that leaf; SUMMARY Key Finding "expansion hooks at the turn runner, NOT the ACP handler — keeps `internal/acp` protocol-pure"; PITFALLS 11 ("extract core construction (factory, profile, engine, runner) from `runACPServe` into a shared builder used by both entrypoints; per-mode code is only the transport") and Pitfall 8's single-sourcing discipline generalized.
- Discretion decision (CONTEXT "Claude's Discretion" — extraction mechanics): the neutral chunk seam is `runtime.ChunkSink` mirroring `acp.ChunkEmitter`'s single method, and prompts cross the seam as `[]session.ContentBlock` (session is core, not protocol) — so `internal/runtime` never imports `internal/acp`, and the acp-side adapter (a ~30-line struct staying in `cmd/ass-guard`) is the ONLY place ACP types touch the core. The `acpDispatcher` renames to `runtime.Dispatcher`-shaped (`engineDispatcher`) as part of the move — it was never ACP-specific.
- `redactorAdapter`, `stubCatalogExec`, `nopHost`, `toProfileDecls`, `realCommandRunner`, `hookSessionTurnRunner`, `hookSessionBoundaryOpener`, `engineTurnRunnerAdapter`, `triggerFromSignal` all move with the Runner — they are core wiring, not transport.
- Provider-factory construction (`loadSchedulingFactory`, `setupProviderFactory`, `firstDeclaredProvider`, `warnLooseConfigPerm`) moves into `internal/runtime` too: the scheduling.yaml load is frontend-agnostic, and leaving it in cmd would force the Telegram entrypoint to either import cmd/ or copy it (the exact Pitfall-11 warning sign "a `runTelegramServe` containing a second copy of factory/engine/session construction"). Verify who else calls these helpers before moving (`cmd/ass-guard/scheduling.go`, `main.go` runTrace) — callers keep working by calling the relocated functions through the runtime package.
