# Plan 10-02 — Telegram bot-token redactor + canary: the secret shape lands BEFORE the first HTTP call

## Phase Goal

**As a** developer away from my IDE, **I want to** drive ass-guard from a Telegram chat — full SDD scenarios over text and voice, on the same engine ACP uses — **so that** the agent keeps working wherever I am as a peer surface, not a stripped-down remote.

**This plan's slice:** TG-05, executed with the ordering the research demands. The Telegram bot token matches NO existing redactor pattern (no `Bearer`, no `sk-`) and rides the file-download URL — any transport error or debug log containing that URL prints the credential today. This plan teaches the one redaction chokepoint the token shape and pins it with a canary test, in Wave 1, structurally before any Telegram HTTP call exists in the codebase (Pitfall 9 verbatim: "in P3, before any Telegram HTTP call is written").

## Truths

- Carries TG-05 and the STATE.md standing blocker "[Phase 10]: the bot-token redactor + canary test MUST land before the first Telegram HTTP call (token shape matches no existing redactor pattern)" — this plan IS that landing.
- Research ground truth: PITFALLS Pitfall 9 (the shape, the URL trap, the canary recipe: "after a scripted session configured with a known test-token value, grep the audit log and captured stderr for that value — assert zero occurrences"; the phase rule: "any phase adding a credential-bearing integration adds its secret shape to `redact` in the same phase, with a test").
- The token never has a field name we control: Telegram's own error strings, `FileDownloadLink` URLs, and config echoes carry it inside STRING values — so the regex fallback layer (where `Bearer <tok>` / `sk-…` live today) is the load-bearing insertion point, not the secretKeys JSON-walker.
- Discretion decision (minimal-surface): wire the pattern into the existing fallback regex set and the JSON string-value pass exactly as `sk-` is wired today (read redact.go first and mirror its layering); do NOT introduce a Telegram-specific scrubber type — Pitfall 9's "never a bespoke scrubber" rule.
- Out of scope here (later plans, already covered): the Telegram code's own hygiene (never log the download URL in the first place — 10-06) and header capture discipline (Phase 9, landed).

<objective>
Add the Telegram bot-token regex (`\b\d{6,10}:[A-Za-z0-9_-]{30,}\b`) to `internal/redact`'s scrub layers (error-string fallback + JSON string values, mirroring the existing `sk-`/`Bearer` wiring), with a table-driven test covering the three leak vectors (JSON field value, error string, bot-API download URL) and over-match regressions (times, short pairs, git SHAs), plus a dedicated canary test file planting a synthetic token through every redaction entry point and asserting zero occurrences. This plan touches no Telegram client code — it is the safety net that must exist before the trapeze act starts.
</objective>
