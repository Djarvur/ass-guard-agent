# Plan 03-04 — Runtime capability gate + operator CLI + end-to-end integration

## Phase Goal

**As an** operator, **I want** to validate my scheduling config from the command line and inspect what a tier resolves to at a given time, AND **as a** developer, **I want** the scheduler to never route my tool-using turn to a model that lacks tool-calling — **so that** the tier abstraction is honest end-to-end (capability mismatch is explicit at request time, not just at config-load) and the config is operable without running the full agent.

## Truths

- Implements D-09 runtime side (the request-time capability gate that pairs with D-10's load-time validation — together they make tier mismatch explicit at BOTH authoring and request time): a turn passes a `CapabilityReq{NeedsTools, NeedsStreaming, NeedsThinking}` derived from what the turn needs; the Resolver skips a primary whose `CapabilityProfile` doesn't satisfy the request and walks the fallback chain for the first capable candidate; if no candidate satisfies, Dispatch returns a structured error (the turn does NOT silently run on an incapable model).
- Completes SCHED-06 (capability profiles are documented (Plan 03-01) AND enforced at request time (this plan) — the "explicit, not silent" guarantee) and SCHED-01's operator surface (the developer selects a tier; this plan adds the operator's `ass-guard scheduling validate` + `scheduling resolve` CLI to inspect/configure without running the agent).
- The CLI subcommands (`ass-guard scheduling validate`, `ass-guard scheduling resolve`) are operator tooling — the same cobra-subcommand pattern Phase 1's `profile check` and Phase 2's `acp serve` use. Transport discipline (C1): human-readable output to STDERR by default; `--json` machine-readable output to STDOUT ONLY when explicitly requested.
- The end-to-end integration test exercises the full scheduler: load config → validate → resolve(tier, project, now, capReq) → Dispatch with a fake provider → observe ProviderFallback/CostCeilingWarn events — proving the scheduling abstraction works as one system (the phase-goal promise: "developer never thinks about which concrete model is running; operator manages cost/reliability via config").

<objective>
Close out Phase 3 with (1) the runtime capability gate wired into the Resolver + Dispatch (D-09 request-time — a tool-using turn never routes to a tool-less model; completes SCHED-06 alongside Plan 03-01's load-time validation), (2) the operator CLI (`ass-guard scheduling validate` to check a config, `ass-guard scheduling resolve` to inspect a tier's resolution at a time), and (3) an end-to-end integration test that drives the full scheduler (config → validate → resolve → dispatch with a fake provider → events). The capability-gate test proves a `NeedsTools=true` turn skips a tool-less primary to a tool-capable fallback; the CLI test proves `validate` rejects an inconsistent config to stderr + exits non-zero and `resolve --json` emits machine-readable output to stdout.
</objective>
