# Plan 09-02 — Engine-decision full provenance: "why did it continue" answerable from the log alone

## Phase Goal

**As an** operator of a hands-off agent, **I want to** have every `acp serve` session leave a redacted, bounded audit trail that also records the engine's decisions, **so that** I can answer "what did the agent do, and why did it continue" from the log alone and trust that the mimicry hasn't drifted.

**This plan's slice:** the AUD-04 differentiator — locked D-03: each engine-decision event carries FULL provenance (action + matched signal + the matched text span + source turn + config source). Today `event.EngineDecision{TurnID, Action, Signal, Reason}` and `Manager.AppendEngineDecision(turnID, action, signal, reason)` identify WHICH pattern matched (`text:<patternID>`) but not WHAT text matched or WHICH table entry fired — investigating a continue still requires cross-referencing the assistant message in the transcript. This plan threads span + config source from the pattern-table match site (the only place the span exists) through `Decide` → `Decision` → event + transcript line. It rides entirely on Phase-4 machinery (the engine already emits one decision per turn including nothing) and observes Phase-8-hardened turns.

## Truths

- Carries AUD-04 in full (engine decisions with the matched signal recorded; log-alone answerability) via locked D-03 (full provenance: action + matched signal + matched text span + source turn + config source).
- Research ground truth: ROADMAP success criterion 4; CONTEXT D-03 ("A developer answers 'why did it continue' from the log alone, no transcript cross-referencing required"); SUMMARY Phase-2 "Delivers" (engine-decision events with provenance).
- The TurnID on Decision already IS the source turn (engine/types.go: "TurnID is the source turn the decision is ABOUT (provenance, D-05)") — no new field needed for that slot; the delta is exactly MatchedSpan + ConfigSource.
- Config-source strings are supplied by the TABLE implementation (the engine is table-agnostic — `PatternTable` is an interface): `openspec.toml patterns/<id>` for text matches, `openspec.toml handoff_tools/<id>` for tool matches. This keeps `internal/engine` free of openspec knowledge (existing dependency direction: openspec → engine, never the reverse).
- For the tool signal, the "matched text span" slot carries the tool-call NAME (the turn output carries tool names, not inputs — `TurnOutput.ToolCalls []string`; the name IS the matched signal text). Documented in the field comment so the semantics are explicit, not accidental.
- Cadence invariant (Phase-4 ENG-02): exactly one EngineDecision event + one engine_decision line per turn INCLUDING ActionNothing — this plan enriches fields, never cadence.
- AUD-04's decisions "observe Phase-8-hardened turns" (08-CONTEXT): no engine-behavior change of any kind — `Decide` stays a pure function; only its return carries more evidence.

<objective>
Extend the dual-signal match chain with span + config-source provenance: `engine.PatternTable.MatchText/MatchTool` return a `MatchDetail{ID, Action, Span, ConfigSource}` (zero value = no match), `Decide` populates `Decision.MatchedSpan` + `Decision.ConfigSource`, `event.EngineDecision` and `Manager.AppendEngineDecision` persist both into the bus event and the engine_decision transcript line, and `OpenSpecPatternTable` extracts the span via `regexp.FindString` and names its config entries. Proof: table-driven tests at every layer plus an observe-level test asserting a continue decision line answers "why" from the line alone.
</objective>
