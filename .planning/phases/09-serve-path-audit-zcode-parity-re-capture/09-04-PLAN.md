# Plan 09-04 — The re-capture run: operator workload, drift report, re-pin, re-baseline

## Phase Goal

**As an** operator of a hands-off agent, **I want** the zcode parity stability test re-grounded on a newly pinned capture session, **so that** I can trust that the mimicry hasn't drifted.

**This plan's slice:** the EXECUTION half of AUD-05 (locked D-04: "run once by the operator in real zcode; that session pins the stability test"). Plan 09-03 built the machinery (pinned-consuming test, canary, version fields, runbook); this plan runs the procedure once: the operator drives the scripted divergence-prone workload in real zcode (the one genuinely human step — it is usage of the MIMICKED agent, and D-04 locks it as operator-run), then the executor automates everything after: threshold verification, drift classification committed BEFORE the profile update, re-extraction with both versions, re-pin, stability green, parity re-baseline. Extraction needs NO API key; only the parity leg is `ZAI_API_KEY`-gated (runbook step 6 — never gate extraction on the key, Pitfall 18).

## Truths

- Carries AUD-05's execution: pinned divergence-prone session produced via the operator runbook, pinned ID consumed by the test, versions recorded, thresholds explicitly re-baselined, drift report committed before any profile update (D-04 verbatim).
- The checkpoint is `checkpoint:human-action` (the 1% class): driving real zcode through the scripted workload — subagent fan-out, mid-session MCP attach/detach — is interactive usage of another agent's UI; there is no CLI/API path. Everything AROUND it (threshold counts, drift report, extraction, re-pin, re-baseline) is automated per the automation-first rule — the checkpoint verifies AFTER automation where possible and gates ONLY the capture itself.
- Research ground truth: PITFALLS Pitfall 17 (the workload requirements + thresholds; warning signs: "a re-capture UAT done in minutes with trivial chat; stability passing on a session using <10 distinct tools; meta not recording the zcode binary version"); Pitfall 18 (drift-before-update ordering; both versions; fresh thresholds; the API-key gating note); ARCHITECTURE Pattern 5 (the re-capture unblocks `internal/profile/stability_test.go`).
- The A/B parity thesis is already proven (v1.0 Phase 1); this plan re-grounds the STABILITY leg and re-baselines parity numbers — it does not re-litigate the thesis.
- Profile content is log-extracted, never hand-written (PROJECT.md Key Decision): the ONLY acceptable mutation of `profiles/zcode/*` in this plan is via `cmd/extract-profile` output + the committed drift report. No manual edits to tools.json/system blocks.
