# Plan 11-04 — Per-model profile selection + the DeepSeek provider entry

## Phase Goal

**As an** operator routing DeepSeek-model turns, **I want** a second mimicry profile whose content is captured from deepseek-harness's real wire traffic, **so that** ass-guard's requests are structurally indistinguishable from dsh's — proving the N-profile thesis with no target-specific code paths.

**This plan's slice:** DSH-04's config half (D-04 verbatim: "profile is specified per-model in config"). Today `--profile` is a serve flag defaulting to zcode; the profile belongs to the invocation, not the model. This plan makes it belong to the MODEL: `ModelConfig` gains a `Profile` field riding the existing Phase-7 machinery; the serve path resolves the turn's model → its profile bundle (the `--profile` flag stays as an explicit override — per-turn switching remains a v1.2 NON-GOAL and is not built). It also lands the DeepSeek provider entry in scheduling.yaml — the opencode gateway per D-01, base-URL-swappable to DeepSeek's official API — plus a probe command that verifies the gateway's OpenAI compatibility mechanically (D-01's "prerequisite verified during the phase").

## Truths

- The profile field is additive config on existing machinery: `ModelConfig` (scheduler/config.go:39) already declares per-(provider,model) provider + pricing + capabilities; `Profile` is one more field; the factory already switches on `prov.Shape` ("openai" → the OpenAI adapter 11-02 just finished).
- Resolution precedence (D-04): explicit `--profile` flag overrides everything (sticky for the session); else the resolved target's `ModelConfig.Profile`; else default "zcode" (back-compat — today's scheduling.yaml has no profile keys; every existing config keeps resolving identically).
- D-01's wording makes gateway verification an in-phase prerequisite: the probe command (one chat-completions round-trip with a trivial tool) runs env-gated against the configured provider; absent credential → loud skip + note (the 09-04 pattern; nothing blocks on keys). If the probe FAILS against the gateway, the fallback is config: point `base_url` at `https://api.deepseek.com` — zero code change (that is the D-01 swappability test).
- DeepSeek dialect facts are capability data (research §4): `deepseek-chat` and `deepseek-reasoner` entries carry Limitations ("ignores sampling parameters in thinking mode", "JSON output can truncate on low max_tokens — size max_tokens generously") — the scheduler's capability machinery (D-09) consumes them; no provider-name branches (11-01 gate).
- Phase 10 will have extracted the turn core to `internal/runtime` before this executes; the profile-resolution hook is written against the actual serve-path file at execution time (read first; the wiring site may be `internal/runtime` or `cmd/ass-guard/acp_serve.go`).
