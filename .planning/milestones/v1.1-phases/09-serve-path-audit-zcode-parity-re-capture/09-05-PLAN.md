# Plan 09-05 — Bounded audit volume: the body_ref pattern + the capped body store (metadata-only events)

## Phase Goal

**As an** operator of a hands-off agent, **I want** every `acp serve` session to leave a redacted, bounded audit trail, **so that** I can answer "what did the agent do" from the log alone without the log eating the disk.

**This plan's slice:** the AUD-03 / D-01 bounding layer. Plan 09-01 made `request_shaped` events flow on the serve path — but each event currently carries the verbatim ~80 KB body (system blocks + up-to-103-tool catalog), and hands-off operation multiplies events (engine continue-injections, hook-DAG send-prompt turns, parallel subagents): hundreds of MB per dogfooding day into append-only files (Pitfall 10's exact arithmetic). This plan implements the body_ref pattern: the event carries the correlation triple + shape fingerprint + content hash; the full REDACTED body lands once in a size-capped, oldest-evicted store retrievable by hash. Discretion decision (CONTEXT): cap = 64 MiB total, oldest-mtime eviction — simple, generous for a day of debugging, no per-file rotation machinery.

## Truths

- Carries AUD-03 (body_ref bounding + loud-never-fatal writes) and completes AUD-02's correlation triple (session/turn/request — the request leg is the hash).
- Locked D-01 verbatim: "Audit events are metadata-only by default — correlation IDs (session/turn/request), shapes, and content hashes; full redacted bodies go to the capped body store, retrievable by hash when debugging. No inline bodies in events."
- This DELIBERATELY supersedes v1.0 Phase-2 D-20's "verbatim shaped outgoing requests" wording for the request line: the transcript keeps its one-writer/one-artifact role (v1.0 D-03/D-20 preserved — CONTEXT binds: "the audit trail complements, never duplicates, the transcript writer"), but the body moves to the store and the transcript line becomes the index to it. The plan documents this supersession at the code site so nobody "restores" inline bodies.
- Research ground truth: PITFALLS Pitfall 10 (body_ref pattern; caps + rotation ~25 MB × keep 3 comparable norm; loud-on-stderr-never-turn-fatal; async off the turn critical path — the TranscriptWriter already drains async, D-05 bounded bus); Pitfall 9 (all captured content through the ONE redaction chokepoint — the store redacts at Put, before anything is on disk).
- The shape fingerprint fields (system-block count, tool count, model, byte length) are exactly the within-session stability invariants (block count / tool set / identity) — parity drift becomes visible by eyeballing consecutive lines, feeding the (deferred) audit-driven parity fingerprint idea without building it.
- The bus payload `event.RequestShaped.VerbatimRequest` is UNCHANGED (transient, in-memory) — adapters, capturer seam, and the 09-01 wiring are untouched; only the CONSUMERS (TranscriptWriter → Manager line) switch to metadata + store.

<objective>
Build `internal/audit.BodyStore` (sha256-keyed, redact-before-store, 64 MiB total cap with oldest-mtime eviction, loud-never-fatal errors), add `audit.SummarizeRequest(body)` producing the shape fingerprint + hash, and convert the RequestShaped transcript path to metadata-only lines: TranscriptWriter summarizes + stores + appends via an extended `Manager.AppendRequestShaped(turnID, profileName, ts, ref, meta)`. Wire one store per serve process in `runACPServe`. Proof: table tests for store/eviction/redaction + a serve-level test asserting consecutive request lines stay ~200 bytes (not ~80 KB) while the body is retrievable by the recorded hash.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-9-18 | Information disclosure | full request bodies (with any provider-injected secrets) persisted in the store | mitigate | Redaction happens INSIDE Put, before any file write (Test 1 pins a secret-bearing body storing redacted); 0600 files / 0700 dirs; the store is content-addressed, not name-addressed, so no session metadata leaks via filenames beyond the hash. |
| T-9-19 | DoS | unbounded store growth in hands-off sessions (Pitfall 10's arithmetic) | mitigate | Total-bytes cap (default 64 MiB) with oldest-mtime eviction; dedup by content hash (identical catalogs stored once — the dominant 80 KB class dedups hard); Test 3 pins eviction. |
| T-9-20 | Tampering | hash divergence between the line's ref and the stored body (investigator misled) | mitigate | ONE shared hash helper computes both the line ref and the store key (specified in the action) — they cannot diverge by construction; Test 8 pins the round-trip. |
| T-9-21 | DoS | store write failures stalling or killing turns | mitigate | Put errors are values; the writer logs to stderr and keeps the metadata line (Test 9) — the audit is an observer, same degradation philosophy as the engine; writes stay off the turn critical path (async bus consumer). |
</threat_model>
