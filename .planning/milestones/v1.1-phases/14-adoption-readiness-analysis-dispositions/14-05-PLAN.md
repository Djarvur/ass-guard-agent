# Plan 14-05 — Token economics: light-tier subagent routing + tool-output truncation

## Phase Goal

**As the** operator about to daily-drive ass-guard, **I want** token costs explicit and bounded —
subagents on the cheap tier by default, oversized tool outputs capped before they eat the window,
**so that** daily use is cost-predictable (Claudecourse #27; ECOSYSTEM-AUDIT §4.4 ECON;
IDEA-LANDSCAPE 🧲-5's economics half).

**This plan's slice:** EARLY-05's two mechanisms. (1) Subagent turns (Task/Agent dispatches) resolve
their model through the scheduler `light` tier when one is configured — the same tiers table that
already routes heavy, no new config surface. (2) A tool-output truncation policy bounds oversized
results at a single chokepoint before they enter the projected window.

Handoff note: light-tier routing is config-conditional — absent a `tiers.light` binding the
subagent keeps the parent model exactly as today; operators wanting out-of-box light-tier routing
must configure the binding (this is the plan's intended reading).

## Truths

- **Light-tier routing design (in-plan decision, rationale grounded):** the routing is a MODEL-level
  override on the established per-dispatch profile copy (subagentProfile already copies the profile
  for agentDef prompts — the Model override rides the same copy; the shared session profile is
  never mutated). A light binding on a DIFFERENT provider than the session's would need a second
  provider instance threaded through the subagent runner — that wider change is routed to the
  post-adoption queue with a loud degrade in the meantime (the override covers the tier's primary
  purpose: a cheaper model on the same wire shape).
- **Truncation cap decision:** DefaultToolResultCapBytes = 131072 (128 KiB). Grounding: the 08-08
  corpus harvest measured the largest observed tool result at ~70KB with NO truncation markers
  anywhere in the corpus — a cap at 128 KiB changes nothing for corpus-scale results (the
  capture-faithful behavior) while bounding the pathological case. Tail-truncation (keep the END —
  the most recent output: error summaries live at the tail) with a leading marker line.
- **Why the append boundary is the chokepoint:** the transcript line is the single source both the
  mid-turn model view AND the Projector's projected window read from — truncating at append time
  covers both with one site (parent-loop results in runTurn AND the subagent Task result).
- The no-confirmation model, boundary machinery, and catalog schema are untouched; subagent
  restricted sets, agentDef handling, and the semaphore path are unchanged.

## Objective

Land both mechanisms with RED→GREEN tests: light-tier model resolution at the subagent dispatch
(configurable via the existing tiers table, loud degrade on cross-provider bindings), and the
bounded tool-output policy at the append chokepoint.

Purpose: EARLY-05 — explicit, test-proven token economics before daily use.
Output: Session.SubagentModel + wiring, the truncation helper + tests.
