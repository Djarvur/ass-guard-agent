# Plan 11-02 — OpenAI adapter: the dsh wire mapping (system form, stream, headers, strict)

## Phase Goal

**As an** operator routing DeepSeek-model turns, **I want** a second mimicry profile whose content is captured from deepseek-harness's real wire traffic, **so that** ass-guard's requests are structurally indistinguishable from dsh's — proving the N-profile thesis with no target-specific code paths.

**This plan's slice:** DSH-02 — the generic half. Today `internal/provider/openai.go` is a MiniMax-validated shell: `buildRequest` (openai.go:108) silently drops `profile.System`, builds `tools` even when empty, sends no profile headers, and its `Stream` returns `errOpenAIStreamNotImplemented` (openai.go:228) while the SERVE path calls `Provider.Stream` (session.go:276/subagent.go:193 — the post-Phase-10 `internal/runtime` home). dsh's wire needs all of it: system message(s) lead the array in the captured form, `stream:true` ALWAYS + `stream_options:{include_usage:true}`, tools omitted entirely when empty, identity headers on the transport, `strict` on function definitions when the capture carries it. Every fact is PROFILE DATA — the adapter gains zero dsh names (the 11-01 gate bans them). The one-vs-N system-message form stays data-driven: `profile.System` is a block list; whatever the extraction (11-05) captured is what goes on the wire, in order, in the captured content form.

## Truths

- Research §5's gap census is the work list: (1) System dropped; (2) Stream not implemented; (3) headers never sent; (4) tools never omitted; (5) strict not threaded; (6) tool_choice only string forms; (7) assistant/tool message-shape not controlled; (8) thinking/reasoning_effort never sent. All eight close here, all data-driven.
- The pinned go-openai v1.42.0 already has `FunctionDefinition.Strict bool` (`json:"strict,omitempty"` — only true ever serializes, matching omit-when-absent discipline) and `*StreamOptions` — verified via `go doc` at research time; NO SDK change.
- The system-form question (one joined message vs multiple) is answered by the CAPTURE in plan 11-05; this plan implements the mechanism that can express EITHER (N blocks → N messages in order, content form per profile field) and tests BOTH forms synthetically. DSH-02's "form decided from the capture, not assumption" is honored by keeping the adapter fully generic and letting 11-05 pin the real form.
- DeepSeek dialect behavior (ignored sampling params, JSON truncation, `finish_reason:"length"`) is capability-keyed (CONTEXT discretion): the response-parsing path treats malformed tool arguments and length-finish as recoverable conditions; capability Limitations live in scheduling.yaml (11-04) — never `if provider == "deepseek"` (the 11-01 gate enforces).
