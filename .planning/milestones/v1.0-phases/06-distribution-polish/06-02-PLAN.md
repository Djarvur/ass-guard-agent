# Plan 06-02 — Static binary via goreleaser + ACP registry agent.json manifest

## Truths

- Implements D-02 (goreleaser 4 targets — darwin/linux × amd64/arm64 — with `CGO_ENABLED=0` and bundled `time/tzdata`, producing tarballs; `.goreleaser.yml` is the single source of truth for the build matrix; STACK pins goreleaser v2.17) and D-03 (the ACP registry manifest declares how Zed spawns the agent; goreleaser ships the binary the registry points at).
- Carries DIST-01 (single static Go binary via goreleaser, macOS+Linux amd64+arm64, no runtime deps) and DIST-02 (ACP registry `agent.json` manifest so Zed spawns the agent via `zed: acp registry`) at full fidelity.
- **Tier-A correction to D-03 wording (load-bearing):** the CONTEXT/STACK phrasing `command`/`command_args`/`cwd` does NOT match the canonical ACP registry schema (`https://raw.githubusercontent.com/agentclientprotocol/registry/main/agent.schema.json`, fetched 2026-08-09). The real schema requires top-level `id`, `name`, `version`, `description`, `distribution`; spawn is declared per-target as `distribution.binary.<target>.{archive, cmd, args, sha256}`. There is NO `command`, `command_args`, or `cwd` field. Mapping: `command` → `cmd`, `command_args` → `args`, `cwd` is dropped (Zed runs the agent in the opened project's working directory implicitly). This plan implements the REAL schema; the D-03 INTENT (declare the spawn command + args; goreleaser ships the pointed-at binary) is preserved exactly — only the field names are corrected, mirroring the Phase-0 discipline of correcting STACK against the canonical spec (VERIFIED-FACTS item #3 precedent).
- `time/tzdata` is ALREADY blank-imported in `internal/scheduler/init.go` (verified: `TestTzdataBundled` proves IANA zones load) — D-02's "bundled tzdata" holds by inheritance; this plan does NOT re-add the import (a duplicate blank import is a compile error).
- Depends on 06-01: the released binary must CONTAIN the embedded defaults + first-run (D-01/D-04). This plan builds and packages; it does not re-implement seeding.

<objective>
Make ass-guard installable: a single `goreleaser` config produces four static binaries (darwin/linux × amd64/arm64, `CGO_ENABLED=0`, no runtime deps) plus a valid ACP registry `agent.json` so a team running `zed: acp registry` spawns `ass-guard acp serve` correctly. The verify step runs `goreleaser build --snapshot` locally (no publish, no API key) and asserts the four binaries are static, the ldflags-injected `--version` works, and the zero-config first-run from 06-01 succeeds inside a released binary. This is NOT the embed/first-run logic (Plan 06-01) and NOT a live registry publication (that is an operator PR to `agentclientprotocol/registry`, documented but not performed here).
</objective>

<threat_model>
- **T-06-05 (MEDIUM — registry manifest points at the wrong binary / wrong spawn):** if `agent.json` used the superseded `command`/`command_args`/`cwd` fields (per the literal D-03 wording) instead of the canonical `cmd`/`args`, Zed would either reject the manifest or spawn the agent incorrectly — a silent distribution failure where the registry "works" but the agent never starts. Mitigation: T3 implements the REAL schema (Tier-A correction, grounded in the canonical `agent.schema.json`), the acceptance criterion asserts `command`/`command_args`/`cwd` are ABSENT, and the manifest is structurally validated. Severity MEDIUM (no data risk, but a ship-blocker if shipped wrong).
- **T-06-06 (MEDIUM — supply-chain integrity of the released binary):** the distributed binary runs whatever code is in the repo + whatever the toolchain produces; a compromised dependency or a non-reproducible build could ship malicious behavior. Mitigation: `go.sum` pins all deps (already enforced), `CGO_ENABLED=0` removes the C-toolchain attack surface, `goreleaser` builds from the tagged commit, and the per-target `sha256` in `agent.json` lets installers verify the download. The snapshot verify (T4) confirms reproducibility locally. (Full reproducible builds + provenance/SLSA are out of scope for v1 — noted, not blocking.)
- **T-06-07 (LOW — version spoofing via ldflags):** because `Version` is ldflags-injected, a fork/rebuild could spoof a version string in `--version` output. Mitigation: the released archives are the authoritative artifacts (sha256-pinned in `agent.json`); `--version` is informational. Severity LOW (cosmetic).
- **T-06-08 (LOW — `cwd: "."` spawn scope inherited from D-03):** Zed spawns the agent in the opened project's working directory; the agent writes `.ass-guard/` there (T-06-02 in Plan 06-01 already bounds writes to the fixed `.ass-guard/` relative path). No new exposure in this plan beyond what 06-01 already mitigated.
</threat_model>
