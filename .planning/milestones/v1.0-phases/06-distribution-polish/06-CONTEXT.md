<domain>
## Phase Boundary

Phase 6 is ship readiness. A team installs ass-guard via the ACP registry with a single command and gets a working zero-config setup on first launch.

**In scope (3 REQ-IDs):**
- **Static binary (DIST-01):** single Go binary via goreleaser, macOS+Linux amd64+arm64, no runtime deps, CGO_ENABLED=0.
- **ACP registry manifest (DIST-02):** `agent.json` declares `command`/`command_args`/`cwd` so Zed spawns the agent via `zed: acp registry`.
- **Zero-config first run (DIST-03):** default model + pre-seeded zcode profile + pre-seeded openspec.toml — a developer runs an OpenSpec workflow immediately with no configuration.

**Out of scope:**
- Windows support (v2, PLAT-01)
- Telegram peer interface (v2, TG-01..04)
- Additional toolkit adapters (v2, KIT-01..03)

**Mode:** mvp (ROADMAP.md Phase 6). Smallest phase (3 REQ-IDs). STACK pins goreleaser v2.17.

</domain>

<decisions>
## Implementation Decisions

- **D-01:** Zero-config defaults are **embedded in the binary via `go:embed`**: a pre-seeded zcode profile (extracted from a known-good capture), a pre-seeded `openspec.toml` (with real OpenSpec handoff patterns), and a default model config (GLM-5.2 via Z.ai). On first launch, ass-guard writes these to `.ass-guard/` if they don't already exist. Zero network calls on first run. Fully offline-capable. The binary IS the distribution — everything needed ships in it. *[User-selected.]*
- **D-02:** The goreleaser config produces 4 targets (darwin/amd64, darwin/arm64, linux/amd64, linux/arm64) with `CGO_ENABLED=0`, bundled `time/tzdata` (Phase 3 D-03), producing tarballs/archives. The `.goreleaser.yml` is the single source of truth for the build matrix. STACK pins goreleaser v2.17.
- **D-03:** The ACP registry `agent.json` manifest declares: `command: "ass-guard"`, `command_args: ["acp", "serve"]`, `cwd: "."` (or the project root). The manifest is generated by goreleaser as a build artifact. The registry just names the spawn command + args; goreleaser ships the binary the registry points at.
- **D-04:** First-run flow: (1) Zed spawns `ass-guard acp serve` via the registry manifest. (2) ass-guard detects no `.ass-guard/` directory exists → creates it with self-gitignoring `.gitignore` (Phase 2 D-07). (3) Writes embedded defaults: `profiles/zcode/` (pre-seeded profile), `openspec.toml` (pre-seeded patterns), `scheduling.yaml` (default model config). (4) The agent is immediately ready — the developer can run an OpenSpec workflow with no further configuration.

### Claude's Discretion
D-02/D-03/D-04 follow directly from DIST requirements + STACK + prior-phase decisions. Not gray areas.

</decisions>

<specifics>
## Specific Ideas

- The `go:embed` approach (D-01) means the pre-seeded zcode profile is baked into the binary at build time. This profile must be extracted from a known-good zcode capture during the build process (or committed to the repo as a build-time asset). The profile carries a `target_capture_ref` (Phase 1 PROF-03) pointing to the capture it was extracted from — drift detection (Phase 1 PROF-04 / D-08) validates it against the live target.
- The pre-seeded `openspec.toml` carries real OpenSpec handoff patterns (Phase 4 D-14: `[[patterns]]` + `[[handoff_tools]]`). These are seeded from real OpenSpec handoff examples — the Phase 4 researcher extracts them.

</specifics>
