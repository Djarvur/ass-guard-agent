# Plan 06-01 — Tracer: go:embed defaults → zero-config first run → profile loads

## Truths

- Implements D-01 (zero-config defaults embedded in the binary via `go:embed`: pre-seeded zcode profile + pre-seeded `openspec.toml` + default model config `scheduling.yaml`), and D-04 (first-run flow: detect missing `.ass-guard/` → create with self-gitignoring `.gitignore` → write embedded defaults → immediately ready).
- Carries DIST-03 (first run via registry works with sensible defaults — default model + pre-seeded zcode profile + pre-seeded openspec.toml — zero-config) at full fidelity. This is the phase's TRACER slice: it proves the embed → materialize → load path end-to-end before any release tooling (Plan 06-02) is layered on.
- The scheduler's zero-config model config is ALREADY embedded (`internal/scheduler/load.go` `//go:embed defaults/scheduling.yaml`, DIST-03 floor). This plan makes the operator-visible default land on disk under `.ass-guard/` (D-04) so a team can see/edit it, layered over the scheduler's embedded floor.
- `time/tzdata` is already blank-imported (`internal/scheduler/init.go`) — D-02's tzdata requirement is satisfied by inheritance; this plan does not re-add it.

<objective>
Establish the thinnest possible end-to-end slice that proves Phase 6's zero-config promise: a developer drops the ass-guard binary into an empty project, runs `acp serve`, and the agent creates `.ass-guard/` seeded with a working zcode profile + openspec.toml + scheduling.yaml, then loads the seeded profile — with no configuration and no network. This is the TRACER. It is NOT the goreleaser multi-target build (Plan 06-02) and NOT the ACP registry manifest (Plan 06-02). It proves the embed materialization seam is real before release tooling is built.
</objective>

<threat_model>
- **T-06-01 (HIGH — build-operator environment leak via embedded profile):** the dev `profiles/zcode/` contains the operator's absolute paths in `system/block-2.txt` (`/Users/nil/DiskD/W/Djarvur/ass-guard-agent`), `meta.yaml`, and `coverage.yaml` (six `/Users/nil/.zcode/...` paths). Embedding these verbatim would bake the build operator's home directory and project path into the system prompt of every shipped binary — an information-disclosure leak to every downstream team. Mitigation: T1 sanitizes the SEED copy (placeholder `<working_directory>` in block-2.txt; tilde-relative paths in meta.yaml; `coverage.yaml` excluded entirely). Regression nets: T1 acceptance (`grep '/Users/\|/home/' internal/defaults/seed/` empty) + T2's embedded-`Seed` leak-guard test (fails if `/Users/` or `/home/` re-appears in the embed). Severity HIGH because the leak is into a redistributed artifact and is silent (no runtime symptom).
- **T-06-02 (MEDIUM — first-run writes into an uncontrolled project directory):** `Ensure(workDir)` writes files into whatever directory Zed spawned the agent in (`cwd: "."`, D-03). A hostile or mistaken cwd could cause writing into an unexpected location. Mitigation: writes are confined to `.ass-guard/` under `workDir` (fixed relative path, never an arbitrary absolute), modes are 0o644/0o755 (no executable bits), content is the trusted embedded seed (not network-fetched), and the write is non-clobbering (an operator's pre-existing `.ass-guard/` is left untouched). No path traversal is possible (paths are constructed from the fixed `.ass-guard` join + embedded filenames, none of which contain `..`). Verify: T3's test asserts only the expected files appear under `.ass-guard/`.
- **T-06-03 (LOW — stdout discipline regression during first-run logging):** a stray `fmt.Println` in the first-run path would corrupt the ACP stdout channel before the first frame. Mitigation: T4 routes the seeding log to stderr via `log.SetOutput(os.Stderr)` (already the case in `acp serve`); T5's E2E test asserts stdout contains ONLY ACP framing. Severity LOW (deterministic, test-covered).
- **T-06-04 (LOW — cross-phase openspec.toml path mismatch):** OPEN-02 (Phase 4) declares the engine reads `.claude/sdd/openspec.toml`; D-04 (this phase) writes `.ass-guard/openspec.toml`. If Phase 4's engine reads a different path than first-run writes, the seeded defaults are silently inert. Mitigation: this is flagged as a cross-cutting constraint (see must_haves); Phase 4's planner must reconcile the engine's read path with `.ass-guard/openspec.toml` (or first-run writes both). Severity LOW (degrades to "engine asks the user," LRN-01 — not a crash), but tracked.
</threat_model>
