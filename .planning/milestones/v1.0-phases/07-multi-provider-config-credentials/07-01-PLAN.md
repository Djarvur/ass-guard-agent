## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator config file → process | `.ass-guard/scheduling.yaml` (operator-authored, may carry a literal api_key) is read + parsed at startup; an unset `${VAR}` reference or a missing field crosses here. |

| resolved credential → provider wire | the resolved key is placed into the adapter and sent as an X-Api-Key/Authorization header; it must never reach stdout/logs. |

## Surfaced assumptions (do not silently drop)
- **D-02 vs D-06/D-07 reconciliation:** 07-CONTEXT D-02 says the loader "expands `${VAR}` at load time and errors if unset," but D-06 ships an embedded default with `api_key_env: ZAI_API_KEY` (no literal) and D-07 says "do NOT refuse to start ... fail lazy at first use." A load-time fatal on an unset `$ZAI_API_KEY` would break zero-config (the `scheduling validate` CLI, first-run seed validation) and contradict D-07. This plan therefore resolves env references (`api_key_env` AND the `${VAR}` inline form) at FACTORY-CONSTRUCTION time (lazy), not at LOAD time; an unset reference makes the provider uncredentialed (D-07 warn + lazy typed error), never a load fatal. D-02's "clear error naming provider + missing var" is realized as D-07's typed structural error returned on first use. This is a faithful refinement of D-02's literal "at load time," forced by the D-06/D-07 zero-config constraint; flagged for operator awareness.
- **`api_key_env` vs `${VAR}` strictness:** 07-CONTEXT D-03 calls `api_key_env` "an alias for the `${...}` form." This plan treats them with identical (lazy, warn-on-unset) semantics for coherence with D-06/D-07, rather than making `${VAR}` load-fatal and `api_key_env` lazy. If the operator wants the strict load-fatal form for explicit `${VAR}`, that is a one-line change to ResolveCredential later.
- **Scheduler per-turn Dispatch is out of scope:** `NewScheduler`/`Dispatch` have zero production call sites today (only the `scheduling resolve` CLI uses the resolver); the live ACP turn path uses `makeProvider` directly. Phase 7 replaces `makeProvider` with the factory (D-08) and resolves the heavy-tier provider at startup. Full per-turn `Scheduler.Dispatch` integration is a turn-loop architecture change, not a config/credential change, and is NOT in this phase. The factory exposes `Build(providerName)` so a future per-turn wiring is a drop-in.
