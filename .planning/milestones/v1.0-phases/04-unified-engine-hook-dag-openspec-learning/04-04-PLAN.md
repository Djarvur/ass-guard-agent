# Plan 04-04 — Tool execution: concurrent reads, serialized mutations, swappable backends

## Phase Goal

**As the** agent runtime, **I want** read-only tools (Glob, Grep, Read) to execute concurrently within a turn while mutating tools (Bash, Write, Edit) serialize relative to each other, and complex tools (WebSearch, WebFetch) to use a swappable backend, **so that** turns are fast (parallel reads) and safe (no two mutating tools overlap) and backends swap without code changes.

## Truths

- Implements D-21 (concurrent reads, serialized mutations — driven by Phase-2 D-19 mutability field via `toolcat.EffectiveMutability`), D-22 (swappable backends — WebSearch/WebFetch use a configurable Backend interface; the concrete impl is selected at startup from config, no code change to swap). Matches the Claudecourse `isConcurrencySafe()` → parallel-batch vs sequential pattern (RESEARCH §3, §2.4).
- Carries TOOL-04 (read-only tools concurrent within a turn; mutating tools serialize relative to each other) and TOOL-05 (WebSearch/WebFetch use a configurable backend swappable without code changes).
- This plan ships `internal/toolexec` + a small additive `toolcat.Catalog.Register` + a small edit to `session.Session` (replace the inline sequential tool loop with `DispatchBatch` + a `SetToolExecutor` accessor). The session change is minimal: the existing `executeStub` already calls `s.toolExec.Execute` when non-nil — this plan (a) adds the batch dispatcher the loop calls instead of the per-call inline execution, (b) adds a real catalog-backed `ToolExecutor`, and (c) wires it in 04-05's acp_serve edit. HERE the unit tests inject the executor directly into a constructed Session.

<objective>
Ship real tool execution: (1) `DispatchBatch(ctx, exec, catalog, calls) ([]ToolResult, error)` partitions calls by `EffectiveMutability` — read-only batch runs concurrently (errgroup bounded by the provider semaphore or a fixed concurrency limit), mutating calls run strictly sequentially under a per-turn mutex — and returns results in the ORIGINAL arrival order so the transcript is deterministic; (2) a `Backend` interface for WebSearch/WebFetch + a default HTTP impl + a config-selected factory so the backend is swappable without code changes; (3) a `RealExecutor` that implements `toolcat.ToolExecutor` over the catalog (looks up `Tool.Execute`, delegates WebSearch/WebFetch to the configured backend); (4) `toolcat.Catalog.Register(Tool)` so OpenSpec commands (04-02) can be added; (5) `session.Session.SetToolExecutor` + replace the inline tool loop (session.go:125-146) with `DispatchBatch`. Every behavior is tested with a recording executor that sleeps to force overlap + records call order/start times; no live HTTP (the default backend is a fake in tests).
</objective>

// ToolResult is one call's outcome in arrival order (the transcript records
// these deterministically even though read-only calls ran concurrently).
type ToolResult struct {
    CallIndex int             // position in the input calls slice
    Name      string
    Output    json.RawMessage
    Err       error
    IsError   bool
}

// DispatchBatch runs the calls: read-only calls concurrent (bounded), mutating
// calls strictly sequential. Returns results in arrival order (CallIndex).
// D-21 — the turn loop (session.go) calls this instead of the inline loop.
func DispatchBatch(ctx context.Context, exec toolcat.ToolExecutor, catalog *toolcat.Catalog, calls []provider.ToolCall, opts ...BatchOpt) ([]ToolResult, error)

// Backend is the swappable WebSearch/WebFetch implementation (D-22 / TOOL-05).
type Backend interface {
    Name() string
    Search(ctx context.Context, query string) (json.RawMessage, error)   // WebSearch
    Fetch(ctx context.Context, url string) (json.RawMessage, error)      // WebFetch
}

// RealExecutor implements toolcat.ToolExecutor over the catalog. WebSearch and
// WebFetch delegate to the configured Backend; every other tool calls its
// catalog Tool.Execute; unknown tools return a structured error.
type RealExecutor struct {
    Catalog     *toolcat.Catalog
    Backends    map[string]Backend  // keyed by tool name: "WebSearch", "WebFetch"
    Log         *slog.Logger
}

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model → tool dispatch | The model selects tool calls; the dispatcher must execute read-only concurrently + mutating strictly serially or state corrupts. |
| config → backend selection | Operator config selects the WebSearch/WebFetch backend; a misconfigured backend must fail loudly, not silently default to a wrong one. |

## STRIDE Threat Register (canonical Phase-4 IDs)

| Threat ID | Category | Component | Disposition | Mitigation |
|-----------|----------|-----------|-------------|------------|
| T-04-03 | Tampering / race condition | two mutating tools execute concurrently (state corruption) | mitigate | DispatchBatch serializes mutating calls under a per-turn order; T1 Test 2/4 assert no mutating overlap under `-race` via recorded start-monotonic-times |
| T-04-03b | Information disclosure | swappable backend exfiltrates to an unexpected endpoint | mitigate | BackendsFromConfig rejects unknown backend names with a ConfigError (T2 Test 4); the backend URL templates are operator-configured, not model-controlled |
</threat_model>
