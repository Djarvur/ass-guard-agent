# Plan 02-03 — Mutability declaration interface (per-tool field + formula) + runtime tool restriction

## Truths

- Implements D-19 (Mutability = per-tool field in the catalog `Mutability: 'mutating' | 'read-only'`; resolved by SESS-03 formula `mutating if (adapter-class(command) == mutating OR tool.Mutability == mutating) else read-only` — the more-mutating wins; built-in catalog seeds defaults; Phase 4 OpenSpec adapter passes its own Mutability with NO engine change), SESS-02 (mutating commands are ALWAYS boundaries; config may only ADD boundaries, never flip mutating→read-only — enforced structurally), D-10 (subagent restricts execution subset at runtime via a `RestrictedExecutor` wrapper — the model sees the full catalog, the executor enforces which can run).
- Carries SESS-02 (structural enforcement — config adds only), SESS-03 (the formula), PARA-01 (the runtime-restriction half — the goroutine dispatch skeleton is Plan 02-05; this plan builds the restriction wrapper).
- This plan touches ONLY `internal/toolcat` (the formula + per-tool field + restriction wrapper) — zero file overlap with 02-02 (`internal/session`), so it runs in parallel (Wave 2). The Session Core's turn loop (02-02) calls `EffectiveMutability` to decide whether to write a boundary line; that integration is via the public `toolcat` API, no file overlap.

<objective>
Add the mutability-declaration interface to the tool catalog: a per-tool `Mutability` field, the SESS-03 effective-mutability formula (more-mutating wins), the structural enforcement that config can only ADD boundaries (never downgrade), and the runtime tool-restriction wrapper that subagents use (D-10 — the model sees the full catalog, the executor enforces the subset). This is forward-designed for Phase 4's OpenSpec adapter (D-19 — OpenSpec registers commands with their own Mutability, no engine change).
</objective>
