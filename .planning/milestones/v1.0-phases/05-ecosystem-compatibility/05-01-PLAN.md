# Plan 05-01 — Tracer: MCP host core + tool bridge (spawn → list → bridge → call)

## Phase Goal

**As a** Claude Code user with an existing `.mcp.json`, **I want to** point ass-guard at my setup and have my MCP servers' tools appear and work exactly like built-in tools, **so that** my tooling investment carries over unchanged.

## Truths

- Implements D-01 (built-in tools in profile + dynamic MCP discovery at session start; MCP tools are NOT hardcoded in the profile), D-03 (tools/list re-fetched on EVERY connection — no persistent cache; engineered-out N13/N14 schema-drift), D-04 (MCP tools register as `mcp__<server>__<tool>` — Claude-Code naming).
- Carries ECOS-01 (MCP servers hosted as subprocesses via `modelcontextprotocol/go-sdk`; tools bridged into the catalog; callable by the model) and ECOS-03 (tools/list re-fetched per connection).
- This is the TRACER: a real end-to-end `MCP config → spawn → ListTools → register mcp__echo__hello → model tool-call → CallTool → result recorded in transcript` round-trip against a self-exec echo MCP server built with the SAME go-sdk. ECOS-02 lifecycle robustness (process-group + reaper) lands in Plan 05-02; this plan uses the SDK's default subprocess lifecycle (sufficient for the tracer — Plan 05-02 hardens it). The ecosys loader (skills/commands/plugins) is independent and lands in Plan 05-03.

<objective>
Establish the thinnest possible end-to-end proof that a Claude-Code-installed MCP server runs inside ass-guard and its tools are indistinguishable from built-ins: add `modelcontextprotocol/go-sdk` to go.mod, build `internal/mcp.Host` (spawn servers from `.mcp.json` config, Connect, ListTools every connection with NO cache, expose CallTool routing), add `toolcat.Catalog.Register` so MCP tools enter the catalog, add `toolcat.MCPExecutor` (the execution wrapper that routes `mcp__*` calls to the host — exact parallel of the existing `RestrictedExecutor`), and wire `cmd/ass-guard/acp_serve.go:sessionFor` to spawn the host at session/new, merge MCP tool Decls into a per-session profile copy, and wrap the session's executor. The tracer test uses a self-exec echo MCP server (the test binary re-invokes itself as the server via a `TestMain` flag) so the REAL stdio `CommandTransport` path is exercised end-to-end without an external binary dependency.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.mcp.json` → ass-guard | Config crosses here (which servers to spawn, with what env). A malicious `.mcp.json` can request arbitrary subprocesses. |
| ass-guard → MCP subprocess | ass-guard spawns an external process with the developer's privileges; the subprocess speaks JSON-RPC over stdio. |
| MCP subprocess → ass-guard | Tool results cross back; they may contain untrusted content the model will read. |
