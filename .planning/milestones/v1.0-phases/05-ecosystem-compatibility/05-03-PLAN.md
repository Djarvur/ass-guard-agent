# Plan 05-03 — Skills/commands/plugins loader + namespacing (.claude/ read-only + .ass-guard/ own, .claude/ wins)

## Phase Goal

**As a** Claude Code user, **I want** my existing `.claude/` skills, slash-commands, and plugins to load and work unchanged inside ass-guard, with ass-guard's own additions namespaced cleanly under `.ass-guard/`, **so that** switching to ass-guard preserves my tooling investment and ass-guard never clobbers my Claude Code setup.

## Truths

- Implements D-05 (ass-guard's own additions in a separate `.ass-guard/` directory — NOT `.claude/ass-guard/`), D-06 (ass-guard loads from BOTH `.claude/` (read-only) AND `.ass-guard/` (own); `.claude/` wins on conflict; user→project precedence within each), D-07 (Claude-Code discovery rules: SKILL.md, command markdown, plugin manifests).
- Carries ECOS-04 (skills/commands/plugins load from `.claude/` layout, work unchanged) and ECOS-05 (namespacing clean, `.claude/` never clobbered, user→project precedence).
- Independent of MCP hosting (Plans 05-01/05-02): ROADMAP notes "Limited parallelism is possible within Phase 5 (MCP hosting vs the rest)." This plan is "the rest." It produces a discovery/registry that the future Shaper/Session can consult; it does NOT itself execute skills/commands (execution bridging is a downstream concern — v1 surfaces them as discovered + available). MCP server config from `~/.claude.json` is loaded here as the user-scope source the MCP host (05-01) merges with project `.mcp.json`.

<objective>
Build `internal/ecosys`: a loader that discovers Claude Code skills (`<name>/SKILL.md` with YAML frontmatter `name`/`description`/optional `allowed-tools`), slash-commands (`<name>.md` with frontmatter + `$ARGUMENTS`), and plugins (manifest declaring the plugin's skills/commands/MCP servers) from TWO directory trees: `.claude/` (the user's existing Claude Code setup — READ-ONLY, never written) and `.ass-guard/` (ass-guard's own additions). Resolution honors D-06: on a name collision, `.claude/` wins; within each tree, project-scope (`./.claude/`, `./.ass-guard/`) wins over user-scope (`~/.claude/`, `~/.ass-guard/`) — Claude Code's own direction. Read-only enforcement is structural: `.claude/` files are opened only via `os.Open`/`os.ReadFile` (never `os.Create`/`O_WRONLY`/`os.WriteFile`), verified by a test that asserts no `.claude/` path is ever touched for writing. The `.ass-guard/` additions sit alongside the Phase-2 transcripts and Phase-4 learned settings, covered by the existing self-gitignore (D-07).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.claude/` files → ass-guard Registry | ass-guard reads the user's existing setup; a malicious skill/command/plugin file is untrusted content. |
| ass-guard → `.claude/` | ass-guard must NEVER write here (one-way: read-only). A write would clobber the user's Claude Code setup (ECOS-05 violation). |
| `~/.claude.json` → MCP user config | Global config is trusted to the same degree as `.mcp.json` (the developer's own machine). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-08 | Tampering | ass-guard writes to .claude/ (clobber) | mitigate | read-only is STRUCTURAL: only `os.Open`/`os.ReadFile` for `.claude/`; the sole write API (`EnsureGitignore`) is parametrized to `.ass-guard/` and REJECTS `.claude/` paths (T3). Source-level + runtime tests assert this. |
| T-5-09 | Information disclosure | skill/command content read into Registry | accept | skills/commands are the user's own files; their content surfaces to the model the same way Claude Code surfaces them. No special redaction (the content is instructions, not secrets — though if a skill file contains a secret, Phase-2 LOG-03 redaction applies when it reaches the transcript). |
| T-5-10 | Spoofing | `.ass-guard/skills/` name collides with `.claude/skills/` | mitigate | D-06 precedence: `.claude/` wins (T2) — a malicious `.ass-guard/` addition CANNOT shadow a `.claude/` skill. ass-guard's own additions only surface when no conflict exists. |
</threat_model>
